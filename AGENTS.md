# AGENTS.md

`client/` is a Next.js 16 app, `server/` is a FastAPI + PostgreSQL (Neon) API. The root `package.json` only orchestrates dev; there is no JS workspace across the two.

## Commands

- First-time setup: `npm run start` (installs client deps and `uv sync` for the server).
- Both dev servers: `npm run dev` (`dev:api` = uvicorn on :8000, `dev:web` = next on :3000).
- Server tests: `uv run --directory server pytest`; single test: `uv run --directory server pytest tests/test_auth.py::test_name -q`.
- Server lint: `uv run --directory server ruff check .` (py312, line-length 110). Types: `uv run --directory server pyright`; mypy cannot run on this machine.
- Client typecheck: `npx tsc --noEmit` from `client/` (there is no client lint script). Client unit tests: `npm --prefix client test`.

## Server

- Tests use the live Neon DB from `server/.env`: conftest creates a throwaway `solace_test_*` schema and truncates all tables after each test. No offline mode; a pg8000/SQLAlchemy `ConnectionResetError` is a flaky failure, not a code break - rerun.
- Auth tests use the `idp_client` fixture with `FakeZitadel`; music tests use `music_client` with `FakeYouTube` (see `server/tests/conftest.py`).
- Sync SQLAlchemy + pg8000 + explicit `public` schema are deliberate (Neon transaction-mode pooler; this machine's Application Control blocks psycopg/libpq DLLs). Do not switch to asyncpg/psycopg.
- Migrations: `uv run --directory server alembic upgrade head`. Autogenerate falsely wants to drop/recreate schema-qualified FKs, so review every migration by hand. Deploys do not run migrations.
- Errors render as `{"error": "..."}` (handler in `app/main.py`); user-facing schemas are camelCase to match `client/lib/types.ts`, DB columns stay snake_case.
- `server/.env` holds real secrets; `server/.env.example` documents every setting (that file is ignored by the repo's `.env.*` rule and stays untracked).
- MCP: `/mcp` is a Streamable HTTP MCP server (`mcp` v2, stateless + JSON) in `app/mcp_server.py` + `app/mcp_tools.py`, mounted at the root after every `/api` route; the FastAPI lifespan starts its session manager through a stable mount proxy (the SDK manager can only `run()` once per instance, so the app is rebuilt per lifespan). Auth: static `MCP_API_KEY` acting as `MCP_OWNER_EMAIL`, or a Zitadel JWT whose `sub` maps to a member via `(idp_issuer, zitadel_sub)`. `MCP_ALLOWED_HOSTS` is the DNS-rebinding Host allowlist (tests rely on `testserver`; add the deployed hostname). Tools call `app/services/*` directly on a worker thread. Tests: `tests/test_mcp.py` with the `mcp_client` fixture.

## Auth invariants (Elysiaa = Zitadel OIDC, PKCE)

- Guests are DB rows (`POST /api/auth/guest`), not localStorage: kind=guest, `GUEST_TTL_DAYS=7`, seeded with the 17-plant demo garden.
- Signing in while a guest deletes the guest row (DB cascades garden/gifts/sessions) and always provisions the member from the IdP identity. Guest data is never linked to an account; `(idp_issuer, zitadel_sub)` is unique.
- Member logout returns `logoutUrl` (Zitadel `end_session`); the client must navigate there or the IdP cookie survives. The Zitadel app must whitelist `ZITADEL_REDIRECT_URI` and `ZITADEL_POST_LOGOUT_URI`.
- Redirect targets go through `local_path()` in `app/utils.py` - keep same-site `next` values constrained that way.
- Cleanup: `POST /api/maintenance/cleanup-guests` requires header `X-Cleanup-Secret` = `CLEANUP_SECRET` (403 when unset/wrong). CLI equivalent: `uv run --directory server python -m scripts.cleanup_guests [--dry-run]`.

## Client

- Next.js 16 differs from training data; read `client/AGENTS.md` and the docs it points to before writing Next code. That file is regenerated by `next dev` - do not delete it.
- `/api/*` is proxied to FastAPI by the rewrite in `client/next.config.ts` (`API_ORIGIN`, default `http://localhost:8000`); there are no route handlers under `client/app/api`.
- Use `apiFetch` from `client/lib/api-client.ts` for authed calls - it redirects to `/login?next=...` on 401.
- `client/scripts/seed.mjs` and `client/tools/shots*.mjs` assume the old JSON/mock prototype. `npm --prefix client run seed` only writes local JSON; it does not seed the server DB.

## Deploy

- `.github/workflows/cd.yml` builds `server/Dockerfile` (context `./server`) and deploys Cloud Run (`asia-southeast1`), but only on pushes to `master` - the repo's only branch is `main`, so the workflow does not currently fire.
